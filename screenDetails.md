Referral maintenance.
Administrators can amend or cancel referrals or move them to another session (even if that exceeds capacity with a client generated warning). They also accept or reject the referrals that are waiting for a decision.

#Buttons and other controls
Whether a button can be used is said by its colour, the same way on every screen in the application: an available button follows its work category — green for sessions, red for referrals and blue for stock — an unavailable one is grey, and the text on each is whatever colour keeps it readable. A control that works must never be distinguishable from a dead one only by a shade of grey — that is how a team leader comes to report a working stock check as a broken one, and stops pressing it. Colour is never the only signal, and it does not replace what follows: an unavailable control is still reachable and still says why. Each category has a bright brand hue and a darker readable shade drawn from it: the bright hue is for faint background washes and decorative illustration only, and everything a reader must act on or read — a button fill, a control label, an icon that carries meaning, a border, a status pill, a prominent figure — uses the darker shade, so the palette never costs contrast.

Beyond that there is one exception, one quieter shade, and nothing else. An action that cannot be undone from the screen offering it — cancelling a session, deleting a model parcel, cancelling or rejecting a referral — is red and asks an explicit confirmation question before it writes. On a referral screen, where the category is itself red, a destructive action must still be unmistakably not just another referral button; how it is set apart — a deeper shade, or drawing it unfilled — is not yet settled, so for now it keeps the deeper `button-danger` red and the real weight sits in the confirmation question. Deactivating a user or retiring a stock item can be reversed, but still asks first; the stock-item archive mark is also red as a clear warning that it changes whether the item can be used. Where two controls are offered together and only one of them is what the screen is about — the Cancel beside a Save, the Back beside a Next — the other is drawn in the category colour but unfilled, so that it stays unmistakably available without competing. A control that is really a row in a list, or a single word inside a sentence, carries no box at all: a filled block would say it is something it is not.

Links and buttons do not use underlining anywhere in the client. A link keeps its colour, stronger text weight and accessible name, so it remains distinguishable as navigation without an underline; a link drawn as a visible button uses the same border, fill and label language as a button. This applies to text links in lists and tables as well as to controls. A maintenance-table row with an amend or edit action alongside a delete, retire, deactivate, restore or reactivate action uses adjacent compact icons: a pencil for amend or edit, an archive or restore mark for a reversible status change, and a bin only for permanent deletion. Edit and delete controls on the Target lists, Model parcels and Crates tables are plain rather than boxed; a permanent-delete bin is plain red and always opens an `Are you sure?` confirmation. After deleting a row, focus and the spoken status move to a stable nearby control rather than the vanished delete button. Every such icon control says its action and the item it affects to assistive technology and on hover.

#Stock maintenance
Saving a stock-item amendment returns to the same filtered list, brings the amended item into view and focuses its Amend control.

There are about 120 stock items, with a maintenance facility to amend them. A weekly stock take is the source of truth: it shows the direct stock items and crate rows together in shelf order, forty countable rows at a time, and saves each page independently. The current value is visible as a reference, but only a count that differs from it is saved; leaving a row unchanged does not overwrite its history. A counter can return to a saved page and amend it again, and only the change from the most recently saved value is sent. A team lead or administrator can also correct an individual item from the stock list: a plain pencil immediately before its level opens one quantity box and a `Set`, `Add` or `Reduce` choice. `Set` is the default and means the real level now on the shelf; `Add` and `Reduce` are the number to add or take away. An item below its watched low-stock threshold is visibly marked `Low stock` as well as given a pale warning row on the stock list, so the dashboard alert can be followed through to the specific items without relying on colour alone. The stock-take page carries no such marking: it is where a count is recorded, not where the dashboard alert is investigated.
There will also be a list screen with items and current stock, in shelf order, to support the stock take. Its plain Pencil control comes immediately before the on-hand count so the count column remains aligned. Where an item is counted in a packing unit, separate `Count description` and `Count quantity` columns show its configured unit label and the on-hand count in that unit to one decimal place — for example, 40 individual items counted in boxes of 24 show `boxes` and `1.7`; individually counted items leave those two cells blank. On a narrow screen each stock row becomes a labelled card rather than forcing the page sideways.
Stock is maintained in a certain place in the warehouse. So each stock item has a shelf number. A stock item also has a category, which is compulsory and is used to sort stock-item maintenance alphabetically, followed by item name. Pick-list maintenance, stock take and the printed picking sheet are in shelf order, so a picker walks the warehouse once. Shelf order is the plain alphanumeric shelf string, so `A1`, `A10`, `A2` is the required order; numbers inside the label are not interpreted. It has an optional description, which says what the item actually is where its name alone does not. Stock-item maintenance shows and maintains name, category, description, shelf number and an optional low-stock threshold. Each item's amend and retire or reactivate controls are adjacent, compact pencil and archive icons, with their action and item name available to assistive technology and on hover; they are plain icon/text controls, not highlighted boxes. The archive icon is red as a warning and asks for confirmation before retiring; reactivating remains a normal plain control. Leaving a threshold blank means that item is not watched; an active watched item below it appears in the administrator low-stock alert. Units are not maintained.

Crates are maintained as named, explicit member sets and always have a stock-take grouping. Only active stock items make a shelf eligible for a new crate or can be newly added to one; a retired historical member remains visible when its crate is amended. Adding an item to a crate clears its direct grouping, so it is counted only through the crate; removing it, or deleting the crate, restores the crate's grouping to the item for direct counting. Their composition table has headed `Stock %` and `Shopping %` columns; those headings say what the percentage boxes mean, so the screen does not repeat a visible “Stock percentage for [item]” or “Shopping percentage for [item]” beside each box. Each box remains explicitly labelled for assistive technology.

On the grouped stock take, a directly grouped item bought in a packing unit has its ordinary individual-count box and, beside it, a second box headed `or [packing units] of [size]`. Entering the latter immediately fills the individual count with the converted whole-item figure, which is the figure saved. The current-level column states the number alone: its heading already says what the number is, so it does not repeat `individual items`. Crates sit amongst the direct items in shelf order, at their own shelf, rather than following the grouping as a separate block. Each crate row shows its member composition immediately; it is not hidden behind an expand control.

A team leader or administrator can hand the counting to a volunteer who has no account. A Volunteer counting code screen sits on the Stock menu, alongside Stock and Stock take, for both roles; on it, one press generates a single code, shown once — large enough to read out across a warehouse — with the date and time it expires, fourteen days on. The code is displayed with `This is the code to use for doing a stock take.` and a control that copies that text, the code and its expiry together, ready to paste into WhatsApp. The code cannot be shown again: a lost one is replaced by generating another, but every earlier code remains valid until its own expiry time. On the administrator dashboard, an alert links to the Volunteer counting code screen when the most recently generated code has less than five days left before it expires. The alert says when that earlier code expires; it does not reveal a code that was shown only once. The volunteer opens the app, chooses "Doing a stock take?" on the sign-in screen and types that code into a single box — no account, no sign-in. The code is never carried in a link or a web address: it is a live credential, and an address reaches browser history, a shared device's address-bar suggestions and server logs. A working code opens the grouped stock take and nothing else: the shelf list with its groupings and crates, entering counts and saving each page, inside a plain frame with no menu and no route to anywhere else. That frame carries a Finish counting control; because ending deliberately is the only tidy way off a device that never signed in, and a volunteer cannot start again without a fresh code, it asks for confirmation before it clears the code and returns to the code box. When the code has stopped working the screen says so plainly and returns to the code box on its own, with what was typed still in it so a single wrong character can be corrected; there is nothing the counter can do to renew a lapsed code, and a team leader generates a fresh one. What is counted on a code is recorded against the team leader who generated it (server spec, `#Stock maintenance`). The code is held only in memory on the counting device and is never written to it; a reload, or leaving the counting screen, asks for the code again.

#Target stock lists and the shopping list
The domain is in the server spec, `#Target stock lists and shopping`; this is how the two screens behave. An administrator maintains the lists on a Target lists screen, one list at a time: it shows every stock item currently in use, in the same category-then-name order as stock-item maintenance, with a box for the target quantity against each, and only the boxes that have a number in them are kept — emptying a box removes that item from the list on the next save. A target must be a whole number of one or more; a zero is refused, with the advice to clear the box instead. If the list still names an item that has since been retired or removed from the catalogue, that line is set apart in a "lines that need attention" panel and the list cannot be saved until each one is dealt with — removed here, or the stock item brought back on the stock items screen. An item that has only been renamed is not held up: it appears under its current name with the stored target filled in and a quiet note that the older name will be updated when the list is saved. A list has a name, editable, unique among the lists; there is no retire state, only delete. Its list-row amend and delete controls are adjacent, compact pencil and bin icons, with their action and list name available to assistive technology and on hover. Maintaining the lists is an administrator task and is not on a team leader's menu.

A team leader does the food shopping, and the Shopping screen is on both an administrator's and a team leader's menu. Above the target-list selector is a calculation choice. Its normal choice, `Bring stock up to target`, works out what to buy for each item on the list: the target less what the last stock take says is on hand, treated as nothing where that figure has gone negative, shown only where that comes out above zero — an item already at or above its target is simply absent. An administrator also has `Cover session requirements through Saturday`. After they select a target list and ask the screen to calculate, it prepares any missing pick lists for every open session from today through Saturday night, one session at a time using the maintained preference rules. It then shows each selected-list item whose aggregate requirement in those still-open sessions exceeds current stock; the list's quantities are a scope, not part of this calculation. A crate line scopes each of that crate's current member items. This mode is administrator-only because its server requirements report is administrator-only; a team leader sees a short explanation rather than a control that would fail for them. The result is grouped by category, with the categories in alphabetical order and the items alphabetical by name within each. This is the one place stock is deliberately not in shelf order: the person reading it is walking a supermarket, not the warehouse. A team leader can amend a displayed quantity for this run in a compact field beside the item; its accessible name is not printed on the screen, and the changed number is what prints and copies. It prints on A4 landscape in three columns, filled down the first column before the second and the second before the third, with each category heading kept together with its items rather than split across a column or page. The printed sheet is plain text and quantities, without input boxes or reset controls. A "copy to clipboard" button puts the same list on the clipboard as plain text — a category heading on its own line, then a tab between each item name and its quantity — ready to paste into a spreadsheet. A requirements-mode printed heading names its Saturday-night cut-off.

The Shopping screen never stops a team leader, and it counts every mismatch between the chosen list and the current catalogue into one on-screen note — "N items need an administrator's attention". Where the list names an item that has been renamed, that item is still bought: it appears in its category with the quantity to buy, marked with the name it used to have, and it is one of the N. Where the list names an item that has been retired or is no longer in the catalogue, that item is not bought — it is left out of the category groups and instead named in that note with only its target quantity, since there is no stock figure for it, and it too is one of the N. The same marks and the same "needs an administrator's attention" list are carried onto the printed sheet and the clipboard copy, so whoever does the shopping or files the sheet afterwards sees the whole picture. Sorting the discrepancies out is the administrator's job, on the Target lists screen, and it is never in the team leader's way.

There is also a fresh-food shopping list. It is distinct from the standing target-stock list: a team leader selects sessions from today to an end date, initially the end of the current week, and asks the screen to build any missing pick lists one referral at a time using the maintained preference rules. It then shows the positive shortfall across pick lists for sessions not yet complete, ignoring `-1` quantities and treating a negative stock take as zero. Whether stock already on hand is subtracted for each fresh item is not yet decided; the screen cannot offer the list until that freshness policy is settled.

#Christmas voucher and first-time selection
An administrator-only `Christmas vouchers` screen under Master Data maintains one `Voucher dates` range, with a start date and an end date. The scheme applies to sessions on or between those dates. It does not determine a client’s referral history. Instead, the administrator’s referral-review process includes a dedicated first-time review screen for that work: for each referral, an administrator selects the client’s last session date or `No previous referral` and saves it. Saving changes the first-time-review value from `Admin` to the recorded choice. The chooser shows every session, not only sessions whose households attended. A No Show or Not in referral remains shown but cannot be selected. A referral still pending is included and selectable whether it awaits approval of its referrer, an administrator’s review, or the session itself.

There is no first-time-review button before the decision is recorded. When an unreviewed referral has one or more possible matches, opening the referral goes directly to the Previous attendance screen. Its Back control returns to the referral list, rather than the referral which would immediately send the administrator back to the screen. When it has none, the system records no previous attendance immediately and does not show that screen. Once a decision is recorded, the referral shows its usual previous-referrals summary and a `Review previous attendance` link. Reopening the screen confirms that the decision has already been recorded and its Back control returns to that referral.

The Previous attendance screen is headed `Potential matches`. It puts the referral being submitted — name, date of birth, masked phone number, postcode and address — above a table of possible matches. The table has a radio selection, client, match fields, date of birth, masked phone number, postcode, address and last-attended session; No Show or Not in rows remain visible but cannot be selected. It includes a surname-start filter and the existing postcode-match exclusion, a `Never attended / none of these referrals` selection, a Referral check panel, and Back and `Confirm and continue` controls.

When the scheme applies to a pick list’s session, the Run a session client table has a headed `Christmas voucher` column. It says `Refer to administrators for voucher` until the administrator has recorded the previous-referral decision; `Client has already received voucher` where the recorded last session falls in the voucher dates; or `Provide voucher for this client` where there is no previous referral or the recorded last session is outside those dates. This is looked up when the client table is read, rather than saved when the pick list is created, so a pick list generated before the administrator acts shows the current voucher decision. The voucher instruction does not appear on the printed picking sheet.

The Run a session client table has a headed `First-time status` column. It shows `First time` where the administrator has recorded no previous session, or `Admin` where that decision has not yet been made. A recorded previous-session date leaves that column blank.

#Picking list
Against a session there will be an option to view picking list. If that picking list has not been created yet, then it will be done at this point. For each referral, the number of adults and children will result via a series of rules into a model picking list.
This picking list can be easily modified (add new items, change quantities). Pick-list maintenance initially shows only the items selected for the parcel, in shelf order; a retired item remains shown only where that parcel already contains it. It also shows household composition as a compact icon grid: age bands run across its top (crawling baby, child kicking a football, teenager with headphones, adult, older adult with a stick), while rows down its side use the female and male symbols, a neutral person for Non-Binary, and a question mark for Prefer not to say. The numbers are the only visible cell text. Hovering an icon shows what it means — the age band or the gender it stands for — so a team leader who does not recognise a symbol can find out where they are, without a legend taking more room than the grid. It is a convenience for a pointer, not the only way the meaning is available: the labels are read out to anyone using a screen reader whether they hover or not. The same shared grid is used in every display and print location. An initially unchecked checklist, “Show unselected Stock items”, controls whether active items with a blank (zero) quantity are shown. It filters the already-loaded stock catalogue in the client, so checking or unchecking it does not call the database. This generates a printable picking list page per referral, with a pick number and the stock items they require and quantities. The printed sheet remains in shelf order and shows the optional item description under its name when there is one. It carries the same compact household-composition grid.

After picking is complete, modifications can be made to the list.

When a picking list is selected, it must show the referral's answers to the preference questions - the ones on the referral form that are about what the household wants or can eat, such as whether they need flour and whether it should be plain or self raising. These are what guide the person maintaining the list: the model parcel gives the starting point, and the preferences are how it gets adjusted for that household. Without them on the screen the list can only be maintained by guesswork.

This is a screen requirement, not a printing one. What appears on a printed sheet is decided separately, and the reason for referral never appears on either.

#The printed picking sheet
One sheet per parcel, and the whole picking list is printed in one go rather than a sheet at a time.

Every picking sheet is A4 landscape. Its compact heading holds the pick number, household name, delivery details where needed, Information for pickers, and the household-composition grid. The pick number is prominent: it is what matches a sheet to a bag in a hall. The shared composition grid has age icons across its top and gender icons down its side, because that saves vertical space everywhere it appears. The browser print dialog opens as soon as the sheets are ready. The screen keeps a blue, square Open print dialog button for reopening it after it is closed.

The stock items and their quantities are listed in the order the server gives them, which is shelf order, so a picker walks the aisle once. That order is never rearranged on the way to the paper - not alphabetically, not by quantity, not by anything else. They fill three columns down the first, then down the second and then down the third. Each has wrapped item text (and its description where present) beside a separate quantity cell.

The reason for referral never appears on a printed sheet. Not for an administrator either. Sheets are carried round halls and left on tables.

The referee's name goes on every sheet, so that a volunteer handing a bag over can tell it is the right one. Nothing else about them does unless the parcel is a delivery: then the sheet says DELIVERY, and carries the address, the postcode and the phone number, because the address is the point of that sheet and a driver who cannot find the door needs to ring.

Anything the picker needs in order to make up that particular parcel goes on the sheet prominently, because the picker is the only person in a position to act on it. When a pick list is created, configured referral answers are copied into its Pick-list information as a compact labelled snapshot ; for example, Allergies and Beans. Both the box a team lead edits it in and the block it prints in are headed Information for pickers, naming who it is for. The team lead can amend or clear that information while the session remains open. The printed sheet shows only that saved Pick-list information, never live referral answers or the reason for referral.

#Model parcels and the household grid
The "series of rules" that turns a household into a model picking list is a lookup, not a calculation.

There is a table of model picking lists. Each has a name as its key and its contents as JSON - the stock items and quantities that make up that parcel. Its list-row amend and delete controls are adjacent, compact pencil and bin icons, with their action and parcel name available to assistive technology and on hover.

Separately there is a grid of every possible household size. Adults run from 1 to 5 and children from 0 to 5, so there are 30 entries. A household larger than 5 adults counts as 5, and more than 5 children counts as 5. Each grid entry holds just the name of the model picking list to use for that household size, so several household sizes can share one model parcel and changing that parcel updates all of them. The grid is maintained as a whole and updated in one go, so it can be stored as a single row.

A referral must have at least one adult — that is, at least one person aged 12 or over — so every referral maps to a real grid entry.

The model picking lists are not versioned. When a picking list is created for a session, the contents of the relevant model are copied onto each referral's parcel. From then on that parcel holds its own contents and is unaffected by any later change to the model or the grid. The parcel does not record which model it came from - only what is in it.

#Session maintenance
Saving an ad hoc session returns to the same scheduled-session range and completed-session choice; saving a weekly session returns to the weekly list. In each case the amended session is brought into view and its Amend control focused.

Administrators can create and amend either weekly or ad hoc sessions and update the package limit for each. The list they work through is the same table and the same date-and-`Show completed` filters as the Run a session list, differing only in that it offers Add a session, and in that each row opens the session for maintenance rather than for running. Weekly sessions is reached from the Sessions tab's contextual links. A weekly template also has a red, confirmed Delete action: it stops future sessions being generated from that template, while every session already on the calendar remains and can be managed individually.

The Sessions contextual tabs provide the way between scheduled and weekly sessions, so neither list repeats a link to the other. Saving an ad hoc session returns to the scheduled list; saving a weekly session returns to the weekly list, because that is the list it belongs to and the one the administrator was working through.

Each session also carries how many deliveries it can take and, where it takes any, when they go out. Both are maintained here, on weekly and ad hoc sessions alike, and they are asked in that order because the second only means anything once the first is above nought. Staff session tables show how many deliveries are booked against that capacity, with full and over-capacity stated in words as well as colour.

The session's delivery capacity comes first, and it is a number rather than a tick: how many of the session's places may be deliveries. A session of twenty-five might allow eight of them to be delivered, or all twenty-five, or none, and the only thing binding the two figures is that the delivery capacity can never be the larger — a session cannot promise more rounds than it has households. A session that takes no deliveries at all is simply one whose delivery capacity is nought; there is nothing else to set to say so, and no separate flag to disagree with the number. Some sessions have nobody to drive, and a household asking for a delivery to one of them is a promise the food bank cannot keep. **A new session takes no deliveries until somebody says otherwise**, so the box starts at nought: a driver is the exception rather than the assumption, and a session wrongly marked as delivering promises a round nobody is doing. While it stands at nought the two delivery times are greyed out and hold nothing, because there is no window to describe.

Once it is above nought, both times are required. Deliveries go out in a window rather than at a moment — the van cannot arrive at a single minute, so what a household is told is a time to be in between — and a session that delivers without saying when leaves the household with nothing to expect and the reminder message with nothing to quote. A window that ends before it starts is refused. Returning the delivery capacity to nought clears the window rather than leaving it behind, so a session never carries times it does not use. Nothing is scheduled or routed from any of this: it is only what the household is told to expect, and it is what the referral form reads.

**A session that delivers must say when, and these screens deliberately offer no way to avoid it.** The API will accept a delivering session with no window of its own and treat it as delivering across the session's own hours; the charity does not want that, confirmed on 2026-08-16, because the session's own hours are when the hall is open and not when the van is out — that is the whole reason a delivery window exists. So the fallback is not offered here, and this is a decision rather than an omission: anyone finding the gap between what the API allows and what these screens permit should leave it as it is. A session already in that state still reads correctly wherever it is shown, and can be moved out of it but not back.

A session is named to a reader by its date and its hours, and never by its location. The charity runs from one hall, so printing its name on every row and every dropdown option repeated the same words down the page and pushed the parts that do differ off the edge of a phone. The location is still maintained against the session; it is simply not what identifies one. Where the location used to sit, a session that takes no deliveries at all reads `Collection Only`; one whose delivery places have all been taken reads `No deliveries`; and one that can still deliver reads nothing at all — collection is the ordinary case and saying so every time would be the same noise again. What a session's delivery position is worth saying in a list is whether a delivery can still be had from it, never how many places are left: the count is an operational figure, and a referrer who is told nine of ten places are gone learns only that they should hurry. Should the food bank ever run from more than one place, the location has to come back into that line.

Where a session is offered for choosing — a dropdown, or a list of links — it reads as one line of text. Where it is stated as a description of the session being worked on or planned, it reads as aligned columns: the date, the hours, the session's delivery position or nothing, and how many households are booked. **Only where a session is offered to a referrer can that column read `No deliveries`.** The staff lists are told the delivery capacity an administrator set but never how much of it has gone, so they can say that a session takes no deliveries and cannot say that its places have run out; a column that guessed would be worse than one that says less. If the charity wants the fuller answer on those screens, it is the food bank's own records that have to carry the count first. The columns line up down a list so the eye runs along one of them rather than re-finding it on every row, and the empty collection-only cell still holds its place so the count after it stays in line. **Both lists of sessions — the one an administrator maintains and the one a team leader runs from — are the same table, and carry the status as a fifth column**, because a cancelled or a completed session that reads like any other is how somebody comes to run a session that is not happening. One layout rather than two, so a volunteer covering both screens reads the same five things in the same five places. The date heads each row and is what links to the session, being the one part that is never empty and what somebody is looking for when they scan. On a narrow screen the table scrolls sideways within its own frame rather than pushing the page along with it, and can be reached and scrolled from the keyboard.

Both lists are filtered the same way, by a date range and a `Show completed` checkbox above the table. The range opens on the fortnight just gone through the coming six days, which is the work anybody is likely to be looking for and is exactly a team leader's horizon; an administrator sees further out by typing a later date, and is never shown a narrower window than the one they asked for. A start date is always sent, because without one a request for completed sessions would fetch every session the food bank has ever run. `Show completed` starts unticked, so the list somebody opens mid-shift is what is still to do. Ticking it brings in the completed sessions **and the cancelled ones together**, which is the only way either is reached from a list, and the status column is what tells them apart.

#Session processing
Team leaders, and administrators covering for them, have a Run a session option. It lists every open session rather than the calendar-maintenance or referral-maintenance screens. That includes sessions in the past that still need to be completed: outcomes and details are often filled in after the event, so a session that has already happened stays on the list until it is confirmed. A session that has been completed or cancelled is not listed until `Show completed` is ticked, because a finished session is something to look back at rather than work to do. Selecting a session shows its date, time, location and booking count, followed by its clients.

**A completed session opens as a record of what happened, and nothing on it can be changed.** The food bank does not lose sight of a session the moment it is signed off: who attended and who did not, what each household was actually given, the picking sheets as they were printed, the listener sheet and the referral details are all still there to be read, and the text-message conversations can still be followed. A cancelled session opens the same way, and says so; it did not run, so it usually has no pick lists at all, and that reads as an empty session rather than as a fault. Every control that would change something is **absent rather than greyed out**: there is no way to record or take back an outcome, no way to alter a pick list or its Information for pickers, no Mark Pick List reviewed, no Complete Session, no reminders and no replies. A disabled button on a session from three weeks ago says only that something is wrong with the screen, and the reason the screen cannot be changed is stated once at the top instead. Opening the session does not create or reconcile a pick list, opening a message conversation does not mark it read, and printing the sheets again does not record a second printing — the food bank needs to keep knowing when the sheets first went to paper.

Opening an editable session creates a pick list for every active client who does not already have one, only when the household grid provides a model parcel for every active client's household size. Generation is all-or-nothing: if the grid is incomplete, no new pick lists are created and the administrator must complete the grid before staff can run the session. Existing parcels are never changed, so a late referral or transfer gets a new pick list without replacing a picker's adjustments. The client list says whether pick lists have been generated; staff select each client in turn to check and update their parcel. If late parcels are created after the list was printed, the screen says that the list must be printed again.

When a pick list is created, the client applies its maintained preference-rule configuration to the referral answers and current active stock catalogue, then sends the resolved item ids with the creation request. Rules run in configured order; a rule which handles a selected preference answer consumes that answer so a later, broader rule for the same preference handles only the remaining answers. Positive quantities from separately handled answers add together. A rule can select an item at a fixed quantity, or mark it as needing attention where the team lead must decide the quantity; attention overrides any positive quantity for that item. A line needing attention is shown as such rather than as a negative number. It must be given a positive quantity or removed before that parcel can be reviewed, so it cannot be printed or issued. #Referrals
The flow for referrals is that the referrer will put in their email address. This is checked against the charity's list, and either way they are then asked for information about the client. Some information is fixed - the referrer's own name and organisation, the client's first name, surname, date of birth, address, postcode and phone number, the session, the household composition, the main cause of crisis, the collection method and whether they need help with fuel - but some is subject to change. A phone number remains a general contact number, so a landline or a number from outside the UK is accepted. Where an entered number identifies itself as a UK mobile — written with a national `07` prefix or an international `+44`/`0044` prefix — it must have a valid mobile prefix and exactly the right number of digits, after spaces and ordinary punctuation are ignored. This catches a mistyped UK mobile before it is stored and later used for a session reminder, without treating a non-mobile contact number as invalid. Household composition is one grid with age ranges down the left (0-4, 5-11, 12-17, 18 to State Pension age, State Pension age or over) and Female, Male, Non-Binary and Prefer not to say across the top. Empty cells are shown blank and only non-zero counts are retained in the `Household Components` JSON answer. The client derives the fixed operational fields from the grid, and they are sizing figures rather than a description of the household: an adult is anyone aged 12 or over, a child is anyone aged 5 to 11, and the under-fives count towards neither. A teenager eats an adult's share and an infant is fed from elsewhere, so those two counts are what the household grid and the preference rules run on. The grid itself is retained for reporting, and it is the grid — never the two counts — that describes who lives in the household. A referral must include at least one person aged 12 or over. The confirmation shown back to a referrer is the exception: it counts the household the way the two words are normally used, adults being everyone 18 or over and children everyone under 18, so a referrer can recognise the household they have just entered. Collection method is a structured operational value rather than a JSON answer: `Delivery Requested` maps to delivery, `Referrer will collect` maps to referrer collection, and every other collection answer maps to collection. Its derived delivery state is true only for delivery. A `No Answer` questionnaire row is display-only text and has no response or JSON key. A question allowing at most one choice is a dropdown; a required question with no default begins with `-- choose --`, and no separate choice instruction is shown. Questions allowing more than one choice remain checkboxes with their instruction. The actual questions to be asked and the validation for them will be in a json config file as part of the client. This is replacing a google form, so basic validation of drop downs, radio buttons, free form text, number validation etc.
This is then submitted to the server.
The session that the client will attend will be from a drop down of the available sessions (non full) for the net 2 weeks. A session on that list has room for the household; it may still have no room for a delivery, which is a separate answer and is said against the session on the line below.

The questions come from the charity's live google form, which has now been reviewed and supplied. The fixed fields above are settled and so are the additional questions; what remains open is the wording of some option lists, and those are listed as open questions rather than guessed at on screen.

Asking for a delivery takes two confirmations together: that the client meets the criteria for delivery, and that the client will be at home for the delivery time. Both are ticked or the form does not move on, because either alone is not what is being asked. Directly above them the form states the chosen session's delivery window and the date it falls on, so the second confirmation is about a real time a referrer can put to a household rather than an abstraction. That line carries a bold label, "Delivery Time:", with the window itself in ordinary text after it, and it is set at the same size and contrast as the questions around it rather than as small print: it is the one line the confirmation beneath it asks a referrer to agree to, and written as a plain sentence it was read straight past. That line is written into the questionnaire configuration as a variable the chosen session fills in, not as a question hard-coded into the screen, so it stays maintained the same way every other question is. It follows that the session is asked before the collection method: it is the answer both the line and the confirmation depend on, and until a session is chosen the line and the confirmation are simply not shown.

That line says one of three things, because there are three positions a session can be in. Where it delivers and has room, it quotes the window and the date. Where it has nobody to drive, it says that no deliveries are available for the session. Where it does deliver but its delivery places have all been taken, it says that no delivery slots are available for it. The last two are near enough the same words for the same reason — a referrer reads whichever applies and never the pair, and both answer the only question being asked, which is whether this session can bring the food to the door.

**The form states the position and does not police it.** Delivery stays on offer whichever of the three the line reads, and the form still moves on and still submits. It is not asked to check what it has just told the referrer: a referrer who has read that line has already been told, and a second refusal from the form a moment later would add nothing. The only case a check could catch is the one where the last delivery place goes between the line being read and the form being sent, and no amount of checking on the form's side can win that race.

The food bank itself refuses what it cannot do, which is the change from what went before. A referral to a session that has filled, a delivery to one whose delivery places are gone, and any referral at all once the session's cutoff has passed are all refused outright, rather than taken and left for an administrator to catch. So are the two the list would never have offered in the first place — a session cancelled, and one already signed off — because either can happen while a referrer is still filling the form in. A promise the food bank cannot keep should not be one a referrer is left to make. A collection is never affected by a session's delivery capacity, however full it is; only a delivery is turned away.

A refusal is one thing; silence is another. Where the food bank never answers at all — the connection drops, or something fails at its own end — the form does not know whether the referral reached it, and says exactly that: it may or may not have arrived, it must not be sent again, and the referrer should phone the food bank to find out. Sending it again is the one thing that must not be offered there, because a referral that did arrive and is sent a second time books the household in twice and takes two places on a session another household needed. That is the opposite of a refusal, which the food bank has told us wrote nothing and which the referrer is free to correct and send again.

A referrer whose referral is refused is put back on the first page of the form, where every one of those answers is given, with a dramatic red `FAILED!!` heading above it. It then says in ordinary red text, `This client could not be referred for the selected session`, followed by `Reason:` and the food bank's own sentence in black. That sentence is the only thing said about the cause, and it is the food bank's to write: the refusals are one status between them, and a form that tried to work out which had happened would be guessing from wording the food bank is free to change. **Nothing they have typed is lost.** The refusal is a race and not a mistake — what they chose was true of the list when they chose it — so it is answered as a recovery rather than as an error: they arrive at the page holding the answer to change, and the form does not add words of its own about a cause it cannot identify. The list of sessions is fetched again as they arrive, so a session that has just filled is no longer offered and the same choice cannot be made twice; where the session they had chosen has gone from the list, that answer is cleared with it rather than left standing as a choice they can no longer see.

Where what was refused was the delivery, the confirmation that the client will be at home for the delivery time is taken back with it. The session they choose next may deliver in a different window, or the one they keep may now be offering no deliveries at all, and either way the tick would be attesting to a line they were never shown — a referrer must not be left having visibly confirmed something nobody put in front of them. The other confirmation, that the client meets the food bank's criteria for a delivery, stays exactly as they left it: that is a fact about the household and no session can make it wrong, and making somebody answer it again is how a form teaches people to tick without reading. Since the two are only ever given together, taking one back is what brings the referrer back to the delivery time to read it, rather than a courtesy they can click past. None of the other refusals touches either tick: a session that is full, cancelled, already signed off or past its cutoff delivers in exactly the window it always did.

Some questions take their choices from a list the charity maintains on the server rather than from the questionnaire — the secondary cause of crisis is one, offered from the same list of causes as the main one. An answer chosen that way is recorded as a reference to the entry rather than as its wording, so that renaming a cause does not rewrite the referrals that named it. **Nobody is ever shown that reference.** Wherever such an answer is read back — the referral itself, a printed sheet, a working list, the spreadsheet extract — it reads as the words the answer was chosen by, and a screen that cannot reach the list does not show the answer at all until it can. Where the entry has since been retired and the list can no longer name it, the answer says that plainly instead; it never shows the reference, and it never claims the question went unanswered.

Two kinds of question live in that configuration and it is worth keeping them apart. Questions about the person are what the referral is; preference questions - do they need flour, plain or self raising or none - are what the picking list is adjusted from. It is the second kind the picking list screen has to show.

The form is asked a page at a time, with a title on each page, because it is long and a referrer fills it in on a phone. Moving on is refused while something mandatory on the page in front of them is missing, and nothing on a later page is complained about before they have got there. How far through they are is always on the screen.

Where a question allows no answer at all, the screen offers "None" as a choice of its own and starts there unless the form says otherwise. None means none: choosing it clears everything else, choosing anything else clears it, and it is not recorded as an answer. Where a question allows several answers, the screen says how many may be chosen and stops accepting more once that many are.

A question that only applies because of an earlier answer is greyed out until that answer is given, and anything already typed into it is forgotten when it greys out again. The referral must never carry an answer to a question that is not on the screen.

The client's postcode is stored in capitals with a single space, however it was typed, because it is searched on and one household spelled three ways matches nothing.

The referrer's email address is checked as they type it, not after they have filled the form in. Somebody the charity does not recognise is told so before they have typed a household's details, not after - but they are not turned away. Their referral is taken and held for an administrator to accept or reject, and the screen says that is what will happen. When the address is recognised, the organisation it belongs to is already known and the form fills that in for them rather than asking - into an empty box only, never over an organisation the referrer has chosen for themselves. When it is not, the form asks which organisation they are from, offering the ones the charity already knows and letting them type one that is not there.

Recognising somebody is said as soon as it is known, but not recognising somebody is only said once they have finished with the address and moved on. Half of a real address looks like a whole one - pete@guildford.gov on the way to pete@guildford.gov.uk - and the charity does not tell a referrer it has never heard of them over an address they are still typing. Editing the address again takes the statement back until they have finished with it once more.

A household larger than the grid allows is not an error and is not shown as one. Anything over five adults or five children counts as five, so a household of nine receives the same parcel as five. If the screen says anything about it at all, it says it as information.

The last page carries a security check, because this is the one form anybody on the internet can send and the food bank cannot have a machine filling it in. It sits immediately above Send, where the referrer can see what they are waiting for, and it is labelled as what it is. Send waits until the check has passed and says so in a sentence beneath it - a button that cannot be pressed and does not say why reads as a broken form to somebody who has just spent twenty minutes on seven pages. The check renews itself quietly: it goes stale after a few minutes, and somebody re-reading their answers before sending should never learn that it did. If the check cannot pass at all, the screen says so and says to phone the food bank, and it never tells anybody to reload the page - nothing they have typed is saved anywhere, so that advice would throw away the whole referral.

Where the food bank has not configured a security check, there is none and nothing on the screen refers to one. That is the same arrangement the rest of the system uses for a facility that is switched on by configuration: it is off, rather than half-present.

#After a referral is submitted
The referrer cannot change or withdraw a referral once it is submitted. There is no self-service route at all, and there is no window in which there is one.

Instead the screen confirms what was sent, showing back every answer that had to be given, because that is the referrer's only chance to notice that a surname or a session date is wrong. The session and the reason for referral are shown as the words the referrer chose them by - the session as its date, time and location, the reason as its wording - and never as the internal identifiers they are submitted as, because a referrer cannot check an identifier and checking is the only thing this screen is for. A referral that is waiting to be accepted says so plainly, so that nobody leaves believing a household is booked in when it is not. A `Refer someone else` button starts another referral, retaining the referrer's name, email address, organisation and contact number only; every client, household, session, collection and other questionnaire answer starts again.

To change anything after that the referrer telephones the food bank and an administrator makes the change. The screen says so plainly. This is a normal ending, not a fault, and it is not apologised for.

#Referrals awaiting a decision
Marking a referral reviewed or cancelling it returns an administrator who opened it from the referral list to that same filtered list; where the changed row remains in the list it is brought into view and focused.

A referral from an email address the charity does not recognise is held until an administrator accepts or rejects it. It holds its place on the session from the moment it is sent: it counts against capacity, a parcel is picked for it, and it appears on the pick list and the printed sheets like any other. Unless an administrator rejects it, the household is presumed to be a genuine client.

What the referrer is told is deliberately more cautious than that, and the two must not be reconciled. The confirmation screen tells the referrer the household is not booked in yet and that nobody should turn up until the food bank confirms it, because the referral genuinely may still be rejected and a household turned away at the door is the worst outcome there is. The food bank contacts the household one way or the other. But contact is not always possible, and a household who never got the message may turn up anyway — so the team leader has their parcel ready and serves them. One statement is advice to a referrer, the other is what the session actually does; neither is a mistake in the other's terms.

Two quite different things happen to a referral, and the screens must never let them read as one. The first is a decision about the **referrer**: an unrecognised address means somebody must say whether the charity accepts referrals from them at all, and only some referrals need it. The second is an administrator **reading the referral through**, which every referral waits for whoever sent it. So a referral held on an unrecognised referrer is shown as `Approve referrer`, one that is booked but not yet read through as `Pending review`, and one that has been read as `Reviewed`. The first of those must not be worded with the word review: beside `Reviewed` it reads as the same job at an earlier stage, and it is not — a referral can be approved and still unread, and read without ever having needed approving. A status is shown whole on one line wherever it appears, rather than wrapping within its own outline.

The referral list shows the ones waiting first, and marks each Approve referrer line as needing attention, because a household waiting on a decision is more urgent than one already booked in.

Check referrals has a referral-coloured heading band with its icon, title and short explanation, then a separate panel for the Session and Status filters. Clearing filters removes both filter values and no other URL value; the address continues to contain only a session id and a status where either filter is selected. The results are in a separate table panel with the count above it. Pending-review and delivery labels remain written labels as well as coloured chips. This redesign does not add sorting, export, pagination, overflow menus or any new row action: those are not requirements of this screen.

Accepting or rejecting one takes a single line of comment - why it was let through, or why it was not. There is one comment on a referral and a later review replaces it. It is not timestamped; the referral already records when it was submitted, and that is the date anybody asks about. Only administrators see it, because it can name a referrer or record a suspicion.

When an administrator opens a referral to review it, the screen shows how many earlier referrals appear to be for the same household in the last twelve months and the date of the most recent matching session. The administrator can then choose to show the previous referrals. Each one shows its household details, session date, whether the household attended, did not attend, or is still booked, and which of date of birth, postcode and phone number matched. This information helps the administrator make a judgement; it never blocks accepting, rejecting or reading a referral. The duplicate-referrals section has an `Exclude postcode matches` checkbox, initially unticked. Ticking it recalculates both its count and its list using date of birth and phone number only, so a shared hostel or refuge postcode does not dominate the result. Team leaders do not see the count or previous referrals.

Administrators have a separate referral-search screen, reached from the referrals menu. It searches by date of birth, postcode or phone number; date of birth is the usual search, and postcode and phone number are alternatives. The three read in that order on one line, labelled `DoB`, `or Postcode` and `or Phone number`, so an administrator can see at a glance that the second and third are the fallbacks when a date of birth is not to hand. When more than one is supplied, a referral matching any one is shown, and the screen does not say so in words — the labels carry it. An optional start-of-surname filter is beside the search controls and, used alongside at least one identifier, narrows the result set to distinguish clients sharing a date of birth. Each result has one row: session date, referral status, household name as surname then first name, postcode, phone number, referrer organisation, and a `Notes` column. Notes holds the primary cause, secondary cause, additional crisis information and administrator notes, separated by `/` without subheadings; none is removed. The notes belong in that same row because the office writes there what it learned from ringing the household, and an administrator taking a call needs it at the same moment they need the causes, without opening each referral in turn. The row has a `View` action as well as its coloured name link. The result table can scroll horizontally instead of making its columns wider. Opening a result and coming back is the ordinary way this screen is used — an administrator on the phone works down a list of possible matches — so the referral opened from a result offers a way back to the search results, and returning shows the same search and the same list rather than an empty form. The list must be current: where the referral was changed while it was open — amended, moved, cancelled, accepted, rejected or marked reviewed — the search runs again on return, so an administrator reading the row back to a household on the phone is never reading what it said before the change they just made. That way back is offered only when the search is where the referral was opened from, and the search itself never appears in a web address. The client takes the additional and secondary information from the returned dynamic answers according to the current referral-form configuration; the server does not know what those answer keys mean. It is an administrator-only search because these identifiers and its results are personal information.

Every referral also waits for an administrator to read it through. A referral from a recognised address starts Pending review; once it is read, it becomes Reviewed without changing its booking or parcel. The detail screen offers an administrator a Mark reviewed button once, on the same line as cancelling and moving, while the referral is Pending review — the three are what an administrator does with a referral they have just read, and a button repeated at each end of the page read as two different actions. The referral list highlights Pending review rows so that the referrals still to be read stand out from Reviewed ones.

The referral detail screen shows its header information, then the previous possible referrals, then the approval/rejection and cancellation controls. Its header shows the referral's status and, beside it, what became of the household: Attended/Delivered, No Show/Not in, or still booked. The status alone does not say whether a household that held a place actually came, and that is the first thing an administrator wants when the household is on the phone about a session they missed. What became of the household is shown only where it says something the status does not: a cancelled or rejected referral shows its status alone, because nothing happened on the day and reading that the household is still booked beside the words that say they are not is worse than not being told. An administrator sees the administrator notes directly under the household name and can change just those notes in a small Save/Cancel dialog; the section, its edit control and the dialog all call the field administrator notes, because that is what the office calls what it writes there. The other fixed fields are read-only until an administrator chooses Edit, which expands to the current pages of the referral form. Choosing a page opens the same questions and controls that the referrer saw, with the referral's complete stored answers available for conditional questions. Saving validates and changes that page, preserving every answer from every other page and every stored answer whose key is no longer on the current form; cancelling changes nothing. The administrator’s referral view shows household composition only in the same compact icon grid used for pick lists, and shows every other answer that was actually given, including a stored key no longer on the form, but not a skipped question. It also shows the two operational counts, labelled `Adults (>11)` and `Children (5-11)` so that the ages they cover are on the screen beside them: an administrator is the one person who corrects those numbers, and bare `Adults` would be read as everyone over 18 and corrected to the wrong figure. A team leader is not shown them at all and sees the composition grid in their place. The referral list is the exception and keeps the plain words `adults` and `children`, where the figures are a rough sense of household size rather than something anyone acts on. Marking the referral reviewed, cancelling it and moving it to another session are buttons side by side on one line, because they are what an administrator does having just read the referral through — and cancelling and moving are the two answers to the same phone call, that the household cannot come to this session. Neither acts on the spot: cancelling asks for confirmation and an optional reason, and moving asks which session to move to, warning where the chosen session is already full without refusing the move. The other answers from the referral form come last. The reason-for-referral and session-to-move controls are large enough to read and operate comfortably.

Approving a referral whose referrer the charity does not recognise asks for no reason at all — it is the ordinary outcome, and typing something to explain it is work for nothing — and it writes directly, with no confirming question of its own. Rejecting one does ask, in the rejection dialog and optionally, because there is no review history and that one line is the whole answer to "why was this household turned away?" months later; rejecting also asks the explicit "are you sure" confirming question `#Buttons and other controls` already requires of every destructive action, because turning a household away is not undone from this screen.

#Copying a referral
A household that did not turn up, or whose referral was cancelled or rejected, often rings the food bank afterwards, and the charity gives them another chance. The original referral is the record of what actually happened and is never reopened or altered — the no show stays where it is — so a second chance is a new referral copied from it. The referral detail screen offers an administrator Copy this referral, and offers it only where the referral can no longer be completed: where the household was recorded as No Show/Not in, or where the referral was cancelled or rejected. A referral still on its way to being completed is not copied; moving it is the answer to that phone call, and the two must not be offered as alternatives for the same referral.

The copy carries every detail of the original — the household, its answers, the reason for referral and the referrer — except its status and its session. The administrator chooses the session it goes on from the same picker offered when moving a referral, and is warned but not refused where the chosen session is already full. Unlike a move, the picker offers the session the original is already on: a household who cancelled and rang back can be copied onto the very session they cancelled from, and that is an ordinary phone call rather than an edge case. The copy is approved and read without being asked about either: the administrator making it has just decided that this household should come, so there is nothing left for a later administrator to accept or to read through. Its administrator notes are set to `Copied from referral dated ...`, the date the original referral was submitted, and they replace any notes the original carried rather than being added to them. Once the copy is made the screen shows the new referral, because that is the one the administrator is now working with; the original is left as it stands. Nothing limits an administrator to one copy — a referral that has already been copied can be copied again, and the administrator making it is trusted to know why.

#Session processing screens
A session cannot be closed while anybody on it is still unmarked. When the screen refuses to close a session it names the pick numbers still waiting, because what the team leader needs to know is who is missing.

Marking a referee attended or a delivery delivered is reversible until the session is confirmed, so it is sent directly rather than confirmed. After confirmation no outcome or pick list can be changed.

From the selected Run a session screen, a team leader or administrator can open a referral-details screen for that session. It lists each household on the session with the client name, address, postcode and phone number, and the referrer's name and phone number. It contains no reason for referral, date of birth, answers, review comment or parcel contents. The screen can be printed when the information is needed on paper. On paper every column is a fixed share of the page and wraps onto as many lines as it needs, rather than the table widening to fit its longest entry: a full address and a long name must never push the referrer's telephone number off the right-hand edge of the paper, because nobody discovers a column is missing until they are standing in a hall wanting to ring somebody. The postcode and the two telephone numbers are each given enough room to sit on one line, a number split across two lines being a transcription error waiting to happen. A household stays on one page, and the column headings repeat at the top of each printed page. On screen the table is not held to the width of a sheet of paper; on a narrow screen it scrolls sideways within its own frame, and can be reached and scrolled from the keyboard.

#Listener sheet
From a Run a session screen, a team leader or administrator can open and print one listener sheet for that session after its pick lists have been generated. It is a printed page for the dedicated trained volunteers who discuss the household's situation with clients and offer guidance where appropriate. It includes every non-delivery household except cancelled and rejected referrals. The pick number is printed with the household name, so a listener can match the client to the session list and their parcel. It shows every referral-form column marked for the listener sheet, in the order of the referral form; the marker is the single authority for what a listener sees, and the sheet carries no second fixed list of its own. Where a marked detail is one the listener sheet does not carry, that column is left out altogether rather than standing empty on every sheet. What the charity marks today is the household name, the reason for crisis, the additional information about it, the secondary cause and the fuel-help flag. A single `First time / voucher` column follows those details: it says whether the household is `First time` or needs an administrator, and the current Christmas-voucher instruction where there is one; when both apply it says both. Every column reads as words a listener can say out loud, the secondary cause included — see the referral form's rule about answers chosen from a maintained list. The sheet is not printed at all while that list is unavailable, because a page of references is worse than a page a team leader can fetch again. It never contains an address, postcode, phone number, referrer information, date of birth or parcel contents, and no unmarked answer reaches it. If a new client arrives after the sheet's pick lists were generated, the listener-sheet request is refused rather than showing a partial sheet. The screen says that new clients were assigned and waits for the team leader to acknowledge it; it then regenerates the pick lists and refreshes the client list, and the team leader deliberately chooses Listener sheet again. It is the only printed document on which a team leader may see the reason for referral, and is for the selected listeners only.

#Fuel help list
A fuel administrator signs into one screen: the fuel help list. Administrators can also open it; team leaders cannot. It is a plain table intended to be copied into Excel, with one row for every referral returned by the server. It shows the parcel session date and every answerable referral-form column marked for the fuel team, in the order of the referral form. The marker is the single authority for which client details and answers may appear: the screen does not carry a second fixed list of columns or show any unmarked answer. Where a marked client detail is one the fuel list does not carry, that column is left out altogether rather than standing empty on every row, because a column that never has a value is worse than no column in a table whose purpose is to be pasted into a spreadsheet. The client's date of birth is shown, because some of the organisations the fuel team hands a household on to will not act without an age. It is shown as a date and never as an age, since an age is right on the day it is written down and wrong a year later. Whether the household needs help with energy costs is not a column: every household on this list does, or it would not be listed. Its introductory text does not tell the user how to interpret the permission answer.

#Spreadsheet extract
The administrator-facing screen is titled `Send to Sheets`. A heading band says that confirmed sessions are being sent to the food bank's Google spreadsheet and that this sends household details outside the system. The initial action sits in its own `Run spreadsheet extract` panel. These are presentation changes only: the confirmation, Google permission request, progress, batch limit, failure handling and privacy rules below remain unchanged.

An administrator can start an extract of confirmed, unextracted sessions to the food bank's fixed Google spreadsheet. Starting says that it might take some time and asks whether to continue. Only after they agree does the screen ask that administrator for Google Sheets permission; the Google access token is kept only while the extract is running and is never stored by the food bank system.

The extract finds one completed session at a time, writes every referral on it and one stock-item-usage row to the spreadsheet, marks that session extracted only after both writes succeed, and then continues. It stops after twenty sessions and asks the administrator whether to continue with another batch. Progress is shown while the screen remains open as the number of sessions processed in this run; a session is counted only after its Sheets writes and extracted mark have succeeded. If the browser is closed, reloaded or the machine sleeps, the extract stops and the administrator starts another batch later.

**A run that fails never offers to finish.** It says what went wrong in the words of whatever refused — a spreadsheet whose columns are not the expected ones names the column that disagrees, and what it should have said — and never reports a failure of its own as a failure to reach the food bank's server, which would send somebody to check their connection over a problem in a spreadsheet. It then states that no session was marked extracted and that any session claimed for the run returns to the queue shortly, and offers to carry on or to stop. Carrying on takes up the next session waiting rather than the one that failed, which is still reserved and cannot be taken again until it is released. The word finish is kept for a run that reached the end of the queue, because on a screen that has just failed it reads as finishing the job and invites the belief that pressing it recorded something. Stopping records nothing and never has.

The spreadsheet is a fixed document configured separately for each deployment. Its archive has a hidden first row of immutable column keys and a visible second row of headings which the charity may edit. The extract uses only the hidden keys to place data, preserving the visible headings. Its hidden metadata sheet holds the mapping between an answer key and its column. The extract reads that mapping at the start, puts every answer for the same key into that key's one column, and when it adds a new answer key writes that key to both archive header rows and the metadata sheet; the visible heading starts as the key and may then be changed. A separate `stock item usage` sheet has one row per extracted session: its hidden first row has fixed session keys followed by `stockItem.<id>` keys, and its visible second row starts each stock-item column with that item's name. Its separate `stock item usage mapping` sheet records those keys and their columns. The usage row carries the session id as well as its date and location, so a duplicate can be reconciled. It is written even where no stock was issued, with blank item cells. The extract contains no names, addresses, email addresses or telephone numbers. Its only personal-information columns are postcode and date of birth. Sending is a deliberate action because it sends household details outside the system. A successful spreadsheet write followed by a failed mark can result in duplicate rows; each archive row carries the referral id and each stock-usage row the session id, so a duplicate can be found and removed. The system never retries a timed-out spreadsheet write automatically.

#SMS reminders and replies
The Run a session screen's Text messages tab lets a team leader or administrator send SMS reminders, and carries the total number of unread incoming messages as a badge on the tab itself rather than as a line of text on the page — a small filled circle holding the count, so an unread total is visible without opening the tab. Colour is never the only signal: the count is read in the tab's accessible name as well as shown in the circle, so it is not lost to anyone who cannot see colour. A reminder goes to every household holding a place, including one pending review, but never to a cancelled or rejected referral. The person running the session can press Send SMS reminders again: newly referred households and earlier failures are tried, while households already reminded are not texted twice. The result states how many were sent, how many of those were simulated, failed and already sent, with failures prominent. An individual staff reply states whether it was sent or simulated.

Each household on the session has an expandable message conversation, marked out when it has unread incoming messages. Opening it marks incoming messages read and shows the complete conversation in order. A team leader or administrator can reply from there. The reply control warns that a message must not contain a name, address or anything identifying the household. SMS conversations are never printed or exported.

On a completed or cancelled session the whole panel is read only. The conversations can still be followed, because what a household said is part of the record of that session, but there are no reminders to send and no reply to write, and **opening a conversation no longer marks it read** — an unanswered message from a session weeks ago is exactly what an administrator needs to still be able to find, and scrolling past it must not be what loses it. The unread count is still shown, because it is what makes one findable.

Administrators have an SMS Messages screen, as three tabs: Loose messages, for a reply with no referral behind it at all; Session messages, for everything tied to one, sub-grouped into active sessions and closed sessions; and Referrer messages, for replies from a referrer currently collecting one or more parcels. Splitting them stops a long list of loose replies pushing what a session sent off the bottom of the screen, and keeps a referrer's reply out of a household's conversation. This is not every message in the thirty-day operational record: a phone number that was only ever sent a reminder, and never heard from, has nothing here for anybody to do and is left off the list entirely. A number that does have something to show — a reply, a staff reply, or a failed send — appears as one collapsed line per phone number within its section, carrying the household's name where the messages were assigned to a referral, and the phone number itself when they were not. An unread one says so in words, not by weight or colour alone. Opening a line shows the complete conversation for that number, in order, including any reminders that went — the same way a household's own conversation opens on the Run a session screen. Opening a closed session's or a loose number's line is also what marks its unread replies read, the same way opening a household's conversation on the Run a session screen does: there is nothing further to press. An active session's messages belong to the team leader running it, so opening one here does not mark it read; a closed session's unread replies need administrator attention, the same as an unread loose number's does. A number can appear once per section if its messages were snapshotted against sessions in different states, or against no session at all — closing the session a message arrived under does not detach it from that session or make it loose. A loose number's line is the only kind that shows a phone number in its own right — beside it is a way to Search referrals with the phone number already filled in, and the number never appears in the web address. A referrer-message line has no household name, referral search or automatic assignment: it shows every currently open candidate parcel by session date and time only, each linked for the administrator to inspect and decide manually. It never reaches a team leader. Messages are only a thirty-day operational record, not a permanent household history.
